# 伴侣监控中心 — 工作原理完整说明

> 对应实现版本：伴侣 3.2.102 / 后端 + 前端 2026-08-26 部署。
> 本文说明监控中心从同事电脑到网站页面的完整底层逻辑：每个数据字段的来源、每条告警规则的判定条件、以及已知的短板。

## 1. 这是什么

伴侣监控中心让管理员在网站上一个页面里看到**所有安装了披星云伴侣的电脑**的运行状态：谁在用、哪个版本、在线还是离线、正在干什么、采集和同步是否成功、有没有异常。不需要再一台一台电脑去检查。

**边界（隐私红线，实现上硬性保证）**：

- 只采集**伴侣自己的进程和任务状态**；
- 不采集同事电脑上的其他软件、浏览历史、网页内容、屏幕内容；
- 不提供远程关闭进程、远程卸载等任何控制能力——后端对伴侣只有“接收上报”，没有“下发指令”。

## 2. 数据流向总图

```text
伴侣（同事电脑）                                            披星云服务器
┌──────────────────────────┐    POST /api/v1/companion-monitor/heartbeat
│ 心跳线程：每 45 秒一次      │ ───────────────────────────────────────▶ 后端 NestJS
│ 收集 15+ 字段 + JWT 令牌   │                                          │
└──────────────────────────┘                                          ▼
                                   Postgres 三张表：
                                   • CompanionDevice     每台设备最新状态（1 行/设备）
                                   • CompanionHeartbeat 历史心跳（节流写入）
                                   • CompanionAlert     告警记录
                                                                      │
管理员浏览器 ◀──── 每 30 秒轮询 devices / overview / alerts 接口 ──────┘
（系统 → 伴侣监控中心）
```

没有长连接、没有推送：伴侣主动上报，网页主动拉取。任何一端断线都不影响另一端，断线恢复后数据自动续上。

## 3. 伴侣端：心跳到底上报了什么（companion_heartbeat.py）

### 3.1 节奏

- 伴侣启动后 **10 秒**发第一跳，之后每 **45 秒**一跳；
- 心跳线程是后台守护线程，随伴侣主进程退出，不会残留；
- 还没登录（没有令牌）时**静默不发**，不产生任何网络请求。

### 3.2 每个字段的来源

| 字段 | 含义 | 数据来源 | 隐私说明 |
|---|---|---|---|
| deviceId | 设备唯一标识 | 首次启动时生成 sha1(主机名|网卡MAC|架构|系统) 的前 16 位，保存在 %LOCALAPPDATA%/MatrixFlow/companion_config.json | 只标识电脑本身；配置文件不在更新包里，升级、重装都不变 |
| deviceName | 电脑名 | socket.gethostname() | — |
| loginUser | 当前 Windows 登录用户名 | getpass.getuser() | 用于认出“谁的电脑” |
| companionVersion | 伴侣版本 | 版本号常量（现 3.2.102） | — |
| startedAt | 伴侣进程启动时间 | 进程内计时 | — |
| taskStatus / taskDetail | 当前任务 | 按优先级取第一个命中的：更新中（更新器状态）→ 同步中（抖店同步锁，带店铺名）→ 采集中（采集锁，带账号昵称/进度）→ 排队中（视频剪辑）→ 空闲 | 只读伴侣自己的任务锁与进度变量 |
| taskStartedAt | 任务开始时间 | 任务从“空闲→非空闲”切换的瞬间打点 | 供后端判断任务是否超时 |
| platformSummary | 各平台登录状态 | 抖音/小红书/快手/视频号：读本地 accounts.db 账号表，按平台统计账号数与失效数（有活跃账号=登录正常，全失效=登录失效）；抖店：读本地 config 的 doudian_stores 登录状态 | 只读伴侣自己的账号库；没有该平台的账号就不上报该平台 |
| lastCollection | 最近一次采集结果 | 采集器跑完一轮收尾时调用 record_collection() 打点：成功/失败、采集账号数、错误码 | 存在内存里，伴侣重启后清空，直到下一轮采集 |
| lastSync | 最近一次同步结果 | 抖店同步收尾时调用 record_sync() 打点：成功/失败、上传条数、错误码、店铺名 | 同上，内存态 |
| lastError | 最近一条错误 | 三个来源：采集错误变化、抖店错误变化（对比上次值，变了才记）、心跳自身的网络失败/401 | 只记错误码和一句话消息 |
| update | 自动更新状态 | 读更新器状态：空闲/下载中/目标版本/失败原因 | — |
| recentHttpErrors | 异常请求计数 | 伴侣所有发往 dddddkiii.com 的请求，响应码为 403/404/500 就 +1；心跳成功后清零（每 45 秒一个窗口） | 只统计伴侣自己发出的请求 |
| resources | 自身进程资源 | psutil 只读自己的 PID：CPU%、内存 MB、运行时长 | 不枚举系统进程列表 |
| bootId / seq | 运行周期标识与心跳序号（3.2.103+） | bootId 每次进程启动生成一次；seq 进程内单调递增 | 用于防旧心跳覆盖新状态与崩溃检测 |
| uiMode / startupDiagnostic | 界面模式与启动诊断（3.2.103+） | webview=原生窗口；browser=降级用浏览器打开，附原因（缺 WebView2 组件/渲染失败等）与系统 WebView2 版本 | 解释“为什么这台电脑以浏览器形式打开” |
| lastProgressAt | 任务最近有进展的时间（3.2.103+） | 心跳时比较任务详情快照，快照变化即更新 | 用于卡死判定（有进度不报警） |

### 3.3 发送与失败处理

- 发送：POST {api_url}/companion-monitor/heartbeat，带登录令牌，12 秒超时，直连不走系统代理；
- **401（登录过期）**：令牌有效期 1 小时，过期的第一跳会收到 401。伴侣立刻用保存的账号密码自动重新登录一次，成功后下一条心跳恢复正常——这是设计内的自愈路径，不需要人工处理；
- **网络失败**：只记一条错误，**不弹任何窗口**，不打扰同事使用；
- **成功**：清零 403/404/500 计数；如果之前记的是 401 错误，自动清除该错误显示（3.2.103 起生效）；
- **优雅退出信标**：进程正常退出前发送最后一次心跳（exitState=clean）；崩溃/强杀不会发送，服务端据此识别异常退出。

### 3.4 打点埋在哪

| 打点 | 调用位置 | 触发时机 |
|---|---|---|
| record_collection | companion_collector.py 采集收尾（成功路径与异常路径各一处） | 每轮采集（自动每 30 分钟或手动触发）结束时 |
| record_sync | companion_app.py 的 _run_doudian_store_sync 返回前 | 每次抖店同步（定时每 30 分钟或手动同步）成功时 |
| note_http_error | companion_config.py 的请求头猴补丁 | 伴侣发往本站的每个请求返回 403/404/500 时 |

## 4. 后端：收到心跳后发生了什么（companion-monitor 模块）

### 4.1 鉴权与租户隔离

- 所有请求先过全局 JWT 守卫：心跳接口**任何已登录用户**都能发（同事的伴侣用自己的账号令牌）；
- 查询接口限定 SUPER_ADMIN / OWNER / ADMIN 三个角色；
- 非超管只能看到自己组织内的设备（复用现有组织隔离机制）。

### 4.2 处理每一跳（processHeartbeat）

1. 校验 deviceId 格式（8–128 位字母数字，拒绝脏数据）；
2. upsert 到 CompanionDevice：第一次见到这台设备就建行，否则更新；
3. **字段覆盖保护**：只有心跳里真正带了内容才覆盖旧值——例如某跳没带 lastSync，不会把上次同步记录冲掉；
4. **连续同步失败计数**：只有显式 success=false 才 +1；success=true 清零；success=null（从没同步过）不动。曾经有个 bug 把 null 误算成失败、导致设备被误标异常，已修复并加了回归测试；
5. **历史节流**：如果最近一条历史心跳在 5 分钟内、且任务状态/同步结果/错误码/采集成功/更新状态全都没变，就不写历史表；变了才写一行。否则每台设备每天会写约 2000 行；节流后大约每 5 分钟一行，30 天约 8600 行/设备。

### 4.3 每分钟定时任务（告警的唯一产生者）

**健康状态**（按“距最后心跳多久”判定）：

| 距最后心跳 | 状态 |
|---|---|
| ≤ 2 分钟 | 在线 |
| 2–5 分钟 | 连接不稳定 |
| > 5 分钟 | 离线 |

漏一跳（45 秒没来）不会判离线；判定每分钟跑一次，所以设备关机后最迟约 5 分 45 秒页面才变离线。

**8 类告警规则**（同设备同类告警去重：已有未确认的就不再重复建）：

| 告警 | 条件 |
|---|---|
| 连续同步失败 | 连续失败 ≥ 3 次 |
| 心跳超时 | 5 分钟没心跳 |
| 超 24h 离线 | 24 小时没心跳 |
| 任务卡死（3.2.103+） | 任务运行期间**无进展**超过：采集 15 / 同步 10 / 上传 10 / 更新 30 分钟（持续有进度不报警；旧版伴侣退化为按任务开始时间判定） |
| 自动更新失败 | 更新器状态为 error |
| 版本过旧 | 低于服务端 COMPANION_LATEST_VERSION（现在是 3.2.102） |
| 请求异常增多 | 一个心跳窗口内 403/404/500 ≥ 10 次 |
| 大量登录态失效 | 组织级：24h 内活跃设备中，平台账号失效比例 > 50% 且 ≥ 4 个账号 |
| 疑似崩溃退出（3.2.103+） | 新运行周期开始，而上次运行没有优雅退出信标、且最后心跳距新启动 ≤10 分钟 |

### 4.4 每日清理（凌晨 3:30，北京时间）

- 删除 30 天前的心跳历史；
- 删除 30 天前的告警，以及已确认超过 7 天的告警。

### 4.5 查询接口清单

| 接口 | 用途 |
|---|---|
| POST /companion-monitor/heartbeat | 伴侣上报（任何已登录用户） |
| GET /companion-monitor/devices?filter= | 设备列表；筛选：online / offline / abnormal / version_outdated / collecting / syncing |
| GET /companion-monitor/overview | 健康总览（正常/异常/离线/版本过旧计数、今日采集/同步成功率、最新版本） |
| GET /companion-monitor/alerts?status=open | 告警列表（status=all 查全部） |
| POST /companion-monitor/alerts/:id/acknowledge | 确认告警（唯一的“写”操作） |
| GET /companion-monitor/devices/:id/history?days=7 | 单设备 7/30 天心跳 + 告警历史 |

### 4.6 版本过旧怎么判定

服务端环境变量 COMPANION_LATEST_VERSION 存放“当前已发布的最新伴侣版本”（现在是 3.2.102）。定时任务把每台设备上报的版本和它比较，低了就告警。**发布新伴侣版本时记得更新它**，否则“版本过旧”永远不触发。更新命令：py -3 scripts/set-companion-latest-version.py

### 4.7 测试覆盖

后端单元测试 17 项（backend/test/unit/companion-monitor.service.spec.ts），覆盖：首次心跳建设备、非法 deviceId 拒绝、同步失败计数递增/成功清零/null 不计数、历史节流（5 分钟内不变不写、任务变化即写）、租户隔离（超管不过滤、管理员按组织过滤）、越权访问历史拒绝、离线判定与告警、告警去重、连续 3 次同步失败告警、总览统计、30 天清理。全量后端单测 27 套 240 项全绿。

## 6. 前端页面（系统 → 伴侣监控中心）

- **权限**：菜单和路由都对 SUPER_ADMIN / OWNER / ADMIN 开放；MEMBER / VIEWER 访问会被路由守卫重定向回仪表盘；
- **健康度卡片**：设备总数、正常、异常、离线、版本过旧、今日采集成功率、今日同步成功率、最新版本；
- **设备列表**：设备（名+ID）、使用人、版本、在线状态、当前任务、平台状态、最后采集、最后同步、最近异常、资源（CPU/内存/运行时长）、最后心跳、操作（历史）；
- **筛选**：全部 / 在线 / 离线 / 异常 / 版本过旧 / 正在采集 / 正在同步（筛选在后端执行）；
- **告警面板**：未处理告警列表，每条可点“知道了”确认；
- **历史弹窗**：7 天 / 30 天切换，显示该设备的心跳明细表和告警明细表；
- **自动刷新**：每 30 秒轮询一次；“刷新”按钮立即拉取。

文件：frontend/src/views/admin/CompanionMonitorView.vue、frontend/src/api/companion-monitor.ts、路由 /companion-monitor。

## 7. 已知短板（如实说明）

1. **告警没有推送**：告警只显示在网页里，没有接飞书/微信推送。不打开页面就不会知道新告警。这是最值得补的一块。
2. **最近采集/同步/错误是内存态**：伴侣重启后这三列回到空，直到下一次任务发生才重新有值（设计取舍：不在本地多存一份状态文件）。看到这三列突然变空，多半是伴侣重启过，不是坏了。
3. **故障自动闭环（3.2.103 起）**：同一故障聚合为「事件」并记录发生次数；恢复后先进入 recovering，连续 2 分钟无复发自动 RESOLVED（记录持续时间），同类型的未处理告警也自动关闭。若你已手动点过“知道了”，则保留你的手动状态。
4. **错误列是“最后一条”而非“当前状态”**：像 401 这种已自愈的错误会一直挂着。3.2.103 起心跳恢复成功会自动清除 401 错误显示。
5. **离线判定有固有延迟**：关机/断网后最迟约 5 分 45 秒才显示离线（心跳式监控的正常特性，不是实时探活）。
6. **版本过旧依赖人工维护**：每次发布新伴侣版本要更新服务端 COMPANION_LATEST_VERSION，忘了更新这列就永远为空。
7. **只监控伴侣本身**：伴侣之外的任何东西（系统卡不卡、网络好不好、其他软件崩没崩）都看不到——这是隐私红线决定的，不是功能缺失。

## 8. 常见现象怎么解读

| 你看到的 | 含义 | 要做什么 |
|---|---|---|
| 最近异常显示 HEARTBEAT_401 | 登录令牌到期的那一跳被拒，伴侣已自动重新登录（自愈） | 不用做；3.2.103 起会自动清除显示 |
| 最近异常显示 HEARTBEAT_NETWORK | 某跳心跳网络失败（断网/代理/服务端重启窗口） | 观察是否持续；持续出现才排查那台机器的网络 |
| 设备状态“连接不稳定” | 最后心跳在 2–5 分钟前（漏了几跳，还没到离线） | 多半是网络波动或电脑休眠；变离线再处理 |
| 设备离线 + “心跳超时”告警 | 超过 5 分钟没心跳（关机/断网/伴侣被退出） | 联系那台电脑的使用人确认伴侣是否在运行 |
| 最近采集/同步列突然变空 | 伴侣重启过，内存里的打点清空了 | 等下一轮任务自动填回 |
| 故障已恢复但告警还挂着 | 3.2.103 起恢复后自动关闭（open→recovering→resolved）；若你已手动确认则保留手动状态 | 无需操作；想立刻清掉可点“知道了” |

## 9. 你可以自己验证它真的在工作

1. 打开页面看“最后心跳”时间：应该每 45 秒左右跳一次；
2. 把本机伴侣关掉，等 5 分钟后刷新页面：设备变“离线”并出现“心跳超时”告警；再打开伴侣，约 1 分钟内恢复在线；
3. 跑一轮抖店同步，完成后看“最后同步”列出现时间和条数；
4. 服务端日志里每次心跳都有一行 POST /api/v1/companion-monitor/heartbeat 201（pm2 logs matrixflow）。
